## 二、服务器 / 链路踩坑

### 2.1 服务器旧架构跑不了新模型（架构约束）
- **根因**：`/DATA/hero3/vcmi-build/bin/*.so` 是 ARM64 编译旧 v13 架构（obs 256 维 / 11 动作）；新模型 3464 维 + 4×21×21 地形 CNN + 25 动作，维度与 ABI 都不兼容。
- **结论**：WIN RATE 评测只能在 WSL2（唯一 x86 带新引擎的机器）算，结果回传 :8088 集中存放；**不要迷信"推到服务器评测"**。
- **来源**：`file` 实测 `*.so` 为 aarch64 + 知识库 §五.2。

### 2.2 本机 sandbox 禁用 wsl.exe（环境坑）
- **根因**：本机 WorkBuddy sandbox 将 `wsl.exe` 列入 Program Blacklist，执行报 `PROGRAM BLOCKED BY SECURITY POLICY`。
- **影响**：任何需在 WSL2 内运行的脚本/命令（含 `wsl -d Ubuntu`、训练、评测）都无法在此环境端到端验证。
- **处置**：只写文件（WSL 经 `/mnt/d/` 可见）交用户/WSL 内实跑；语法校验用 Windows 侧 `python -m py_compile` / `bash -n` 兜底；跨机链路文档标注"未在此环境跑通"。
- **来源**：实测。**状态**：环境限制（非代码 bug）。

### 2.3 :8080 推理延迟口径（实测差异，勿混用）
- **现象**：知识库中"2–12ms"与"20–33ms"两个延迟数字并存，看似矛盾。
- **根因**：两者测的是不同口径——
  - **用户实测 2–12ms**：P8 客户端在**局域网本机**对 `:8080/predict` 的往返（网络跳数少）。
  - **sandbox 实测 20–33ms**：服务器响应自带的 `inference_time_ms` 字段（纯服务端推理耗时）；从本机 sandbox 发起的 wall ≈ 73–165ms 因经容器 NAT 跳数，不代表 LAN 客户端。
- **处置**：写文档时两值都标注来源与口径；精确延迟以你 P8 客户端在局域网本机实测为准，不取 sandbox 的 wall。
- **来源**：`curl :8080/openapi.json` 确认 `PredictionResponse.inference_time_ms` 字段 + 8 次实测采样；用户说明（2026-09-24）。**状态**：已厘清口径（见知识库 §5.2）。

### 2.4 跨地图并发评测 worker_crashed（09-24 定谳，对照矩阵坐实）
- **现象**：`batch_eval_pool.py` 12 worker 各开**不同地图**时 ~42% 局 `worker_crashed`（turn=0 早死，VCMI worker 进程死）；同图 12 并发则 0 崩。
- **对照矩阵（KTV × StupidAI，max_turns=2000，全部实跑）**：

  | 条件 | 崩率 |
  |---|---|
  | 串行 4 局 / 串行 12 局 | 0/4、0/12 |
  | 并发 4 worker（全 KTV） | 0/4 |
  | 并发 12 worker（全 KTV） | 0/12 |
  | 并发 12 worker（12 张不同图） | 10/24（~42%） |

- **根因**：跨地图资源竞态，**非并发本身、非段错误**。崩栈（`eu-stack --core`，core 3842659 SIGABRT）：python worker 线程 → `ML::start_vcmi()` → VCMI 资源加载（CAnimation 帧指针已花 `File name: c??\x00`）→ `malloc(): unsorted double linked list corrupted` → glibc abort。机制：VCMI 资源缓存为进程内全局单例，多 worker 同时加载**不同地图**时并发读共享资源路径（`data/` 软链）→ 堆越界。不同图 = 不同资源集 = 触发条件；同图并发无竞态。
- **踩坑 #308（WSL 侧 XDG 缺失）与此无关**：#308 是单服务身份下 VFS 打开失败，已修；本条是评测农场多 worker 跨图 boot 竞态，独立问题。
- **修复方向（harness 层，不动引擎）**：worker boot 阶段 flock 串行化（`flock /DATA/hero3/vcmi/data/.lock`，只锁资源加载、不锁局内运行），或降并发度 + 每 worker 固定同图轮转。验收 = 12 图并发复测崩率 → 0。
- **来源**：09-24 对照矩阵实跑 + coredumpctl/coreA eu-stack 栈。**状态**：🔄 根因定谳，修复（flock）待落。

### 2.5 服务器 core/调试工具链两坑（09-24）
- **坑 1 — libpython 坏链卡死 gdb**：`/usr/lib64/libpython3.11.so.1.0` 软链指向 `/usr/local/lib/libpython3.11.a`（**静态库**，gdb 报 `invalid ELF header`；openEuler 的 gdb 自带 python 扩展被链到它，读 core 直接挂）。workaround：别修链（python 本就是静态构建、无真 .so），改用 **elfutils `eu-stack --core=<core>`** 直接 unwind（不依赖 libpython，无需符号）。
- **坑 2 — 并发评测留孤儿 worker 烧核**：VCMI 线程在父进程被杀后不退出，孤儿 `strategic_worker` 99% CPU 可烧 27min+。每次跑完并发探针必须 `pgrep -f strategic_worker` 清点 + kill。
- **来源**：09-24 实测。**状态**：⚠️ 环境事实，后续 core 分析默认走 eu-stack；并发脚本收尾加孤儿清扫。

### 2.6 WSL 源码同步误覆盖服务器 ML/（09-24 晚事故，09-25 凌晨修复）
- **坑**：WSL `git archive 8679dd35`（WSL 产线）同步到服务器时**声称排除 `ML/` 但实际没排除**（关键源文件 mtime 全变 11:06）→ 服务器 7/25 版 `ML/`（旧 ABI `init_vcmi(IModel*,IModel*,InitArgs&)`）被 WSL 版（`init_vcmi(void*)`）覆盖 → 预编译 `connector_v13.so` dlopen 报 `undefined symbol: _ZN2ML9init_vcmi...`。
- **修复**：`/tmp/ML_server_backup_0924`（同步前备份）`cp -af` 回 `/DATA/hero3/vcmi/ML/`，校验 ABI 符号落回旧签名。
- **纪律**：WSL 归档同步后**必用 `nm -D` 比对 connector 需要的 ABI 符号**，不能只信"排除了"；服务器评测链路权威产线 = 与 connector ABI 匹配的 7/25 服务器版 ML，WSL 只同步非 ML 的 fork 文件。

### 2.7 vcmi-build 是 WSL 拷来的毒构建树（x86 假前置 + python3.12 残留）
- **坑**：服务器 `vcmi-build/`（7 月从 WSL x86_64 拷来的构建树）的 build.make/link.txt/CMakeCache 残留 `/usr/lib/x86_64-linux-gnu/libpython3.12.so` 假前置 + `-lpython3.12`（ARM 服务器只有 python3.11，无 x86 目录）→ 重链 libvcmi.so 时 make 报"没有规则可制作目标 `/usr/lib/x86_64-linux-gnu/libpython3.12.so`"。
- **修复**（外科手术，不重建构建树）：① `sed` 删 `libFacade/CMakeFiles/vcmi.dir/build.make` 里那行假前置；② 两个 link.txt 去 `-lpython3.12`（libvcmi.so 对 python 零引用，安全）；③ 清 .o 重编重链。
- **纪律**：跨架构拷构建树一律当毒药——CMakeCache 里的绝对路径（LIBDIR/前置 .so）全是源架构的。

### 2.8 跨 .so 未定义符号三连（g_adventure_allied_ai / headlessQuit / libvcmi 导出缺失）
- **坑 1 — `g_adventure_allied_ai[64]`**：WSL 08-01 在 `client/Client.cpp` 加 `extern`（ENABLE_ML 时引用）、ML 侧定义；服务器 7/25 版 ML 早于该改动没定义 → 恢复服务器版 ML 后 libmlclient.so 里它是 `U`（未解析）→ dlopen undefined。修复=MLClient.cpp 补 `extern "C" char g_adventure_allied_ai[64]={0}`（空 buffer，Client.cpp 自动回退读 settings，行为零影响）。
- **坑 2 — `headlessQuit`**：定义在 `clientapp/EntryPoint.cpp`（**static，仅可执行体内**），MLClient.cpp 却 `extern` 引用；评测走 in-process `ML::start_vcmi` 不用可执行体 → 共享库链路无人定义。修复=MLClient.cpp 改**局部 static**（同 TU 语义等价，评测链路不走可执行体故无副作用；若日后修好 vcmiclient 需同步改回）。
- **坑 3 — libvcmi.so 导出缺失**：新编 libvcmi.so 只导出 dynsym，缺一批 VCMI vtable/常量（`_ZTV14LobbySetBattleOnlyModeStartInfo` 等，clientcommon 对象引用）→ 链接行加 **`-rdynamic`**（全符号导出，538M）。
- **纪律**：修符号**先做全量 RTLD_NOW 审计**（`LD_BIND_NOW=1` + ctypes 按评测加载序 dlopen 4 库），一次列全缺口；逐个打地鼠（每次冒烟蹦一个新 undefined）是浪费时间。

### 2.9 全池横评进度误读（日志静默≠卡死，ETA 不能按快图外推）
- **坑**：`batch_eval_pool.py` 每张图 16 局**同 worker 串行**、`[map]` 行**只在整图跑完才打印** → 75 分钟只见 1 行，极易误判"卡死"。判活必须看 worker `ps etime/pcpu` + load，不是 grep log。
- **ETA 错**：首版 S-6 写"~08:00 出矩阵"是按第一张快图（early-quit 373s）外推；实际耗时双峰——快图 ~373s vs 慢图（5000 天 cap）单图 ~42000s（11.7h），147 图/32 worker ≈ 4.6 波，真实 ETA 取决于慢图占比（可差 50 倍）。**有效锚点 = 首波 32 行 `[map]` 出现后，单波时长 × 7**。

- **来源**：09-25 04:30 实查（pid 426288 / 1/147 行 / worker etime 1151s / load 356 / KTV 4worker JSON 单局 max 2625s）。见知识库 §5.10。

### 2.10 新 ABI（3464）部署 4 连坑（09-25 上午，知识库 §5.11）
- **坑 1 — 包 `__init__.py` 急加载战斗层**：import `vcmi_gym.envs.v13.strategic_env` 会先执行 root + `envs/v13` 两级 `__init__.py`，它们急载战斗层 `vcmi_env`→`pyconnector`→`exporter_v13.get_global_attribute_mapping()`，而战斗层 enum 与新引擎二进制漂移（`Unexpected attribute: 1` throw）。**战略评测根本不用战斗层**（StrategicEnv 只走 `connector_v13.ThreadConnector` + ctypes 读 `g_strategic_state`）→ 修复=两级 `__init__.py` 战斗层 import 改 try/except guard（战略层保持急载），备份 `.bak_battle`。**v13/v14/v15 connector 必须全编**（缺一个 import 就炸）。
- **坑 2 — `strategic_reader.py` 不在包里**：它在 `hero3_fresh/py/`（项目根旁路模块），`strategic_env.py` L42 `import strategic_reader` 靠 `sys.path[0]` 兜 → 打包 vcmi_gym 时必带 + 跑时 `PYTHONPATH` 含其目录，否则 `ModuleNotFoundError` 后回退分支还带原始 bug（`spec.loader.exec_module(spec.name)`，应为 `(_sr)`，但模块找得到就不走该分支）。
- **坑 3 — CMakeLists 找 libmlclient 走 `${VCMI_DIR}/rel/bin`**：服务器 09-25 重构后 .so 在 `vcmi-build/bin`，而 `vcmi/rel/bin` 还是 7/25 旧件 → 需 `ln -sf vcmi-build/bin/libmlclient.so vcmi/rel/bin/`（symlink，不拷）。
- **坑 4 — `python3 -P` 防影子包**：服务器 `/DATA/hero3` 下另有旧 `vcmi_gym`（256 维 7/29 旧树），CWD 在 `/DATA/hero3` 时 `sys.path[0]` 会把旧包顶上新 `vcmi_gym_new` → 启动必加 `-P`（禁 CWD/用户site进 sys.path）+ 显式 `PYTHONPATH`。
- **纪律**：跨机部署 Python 包前，先 `find` 核包内"被 import 但不在包里"的旁路模块（strategic_reader 型）；跑 `python3 -c "import <pkg>"` 干测 import 链再上真评测。

### 2.11 `tar cCf` 把源文件截成 0 字节（09-25 04:5x 事故，git 救回）
- **坑**：想在 WSL 打包 3464 ML 源时敲 `tar cCf /mnt/d/.../x.tar.gz ML/MLClient.cpp ...`——GNU tar 的 `C`（换目录）选项被解析成了参数的一部分，**`ML/MLClient.cpp` 被当成归档名截断**，WSL 源文件本身变成 0 字节（`md5=d41d8cd` 空文件哈希），且后续 cp/scp 一路传播 0 字节到 D 盘、服务器。
- **修复**：`cd vcmi-native && git checkout -- ML/MLClient.cpp`（HEAD `8679dd35a1` 有完整 26147B，md5 `5fdcacf5`），重传 + 双端 md5 锁死。**系统未坏**（.so 当时还是旧 ABI，未重编）。
- **纪律**：tar 打包用 `tar czf x.tar.gz -C <dir> <files>`（独立选项，空格分开）；任何"传文件后核验"必须 md5 双端比对，**0 字节文件在 `ls -la` 里一眼可见，传完必看字节数不是 0**。

### 2.12 `vcmi-inference` :8080 假死 crash-loop（09-25 修死，双根因）
- **现象**：systemd 状态一直 `activating`，`NRestarts` 飙到 1538；`/health` 有时回 ok（**假象**——是残留老进程在应答，不是 systemd 那个）。
- **根因①**：09-23/24 遗留的老进程（`inference_service.py --help` 实为 server）一直占 :8080 → systemd 每次新拉的进程 `Errno 98 address already in use` 崩 → 无限循环。`ss -tlnp` 抓端口的**真实占用者**才能看见（systemd 之外的残留是惯犯）。
- **根因②**：`/DATA/hero3/vcmi/defender-ipnkyfqb-best3.onnx` 是 38 字节坏文件（内容=拷错的占位文本 `../export/...`）→ onnxruntime 加载时 Protobuf 解析崩。已隔离到 `/DATA/hero3/quarantine/`。
- **修复+验证纪律**：`systemctl stop` → `kill -9` 老残留 → 隔离坏 onnx → `systemctl start` → 判活 = **MainPID 70s 后不变 + journal 近 70s 零 `status=1/FAILURE`**（不能只看 `is-active`，残留在时它也回 ok）。实测 `/predict` 3464 维 obs 出 action（infer_ms≈4）。
- **泛化**：systemd 服务显示 `activating` ≠ 加载中；先 `ss -tlnp` + `pgrep -af <svc>` 找带外残留进程。

### 2.13 ARM64 CI runner 两坑（09-25，CI-ARM64 全绿 run 36063423686）
- **坑 ① — `actions/checkout` rc=128 = git dubious ownership**：runner user 跑 checkout 时 git 判仓目录属主不匹配 → 修 = runner 侧 `sudo -u runner git config --global --add safe.directory \*`（`_work` 目录被 root 碰过即触发；与 WSL 侧同病）。
- **坑 ② — `setup-python@v5` 找不到 3.11 arm64**：python-versions manifest 里 3.11 无 linux-arm64 预构建（arm64 只 3.12+）→ **砍 setup-python，直接吃 runner 系统 `python3.11`**（服务器 `/usr/local/bin/python3.11` 已带 numpy 2.4.6 + gymnasium，engine-free 测试够用）。

## 三、认知纠正（易错点，均经源码核实）

### 3.1 地图格式：战略训练用 vmap，不是 H3M
- 见 1.8。一句话：当前 PPO 训练图全是 `maps/training/*.vmap`；`available_maps.json` 的 110 张 H3M 是经典图另一套。
- 旧知识库 §3.4 曾写"战略训练只用 H3M"，**与源码相反**，已更正（知识库 §二.5）。

### 3.2 动作 10 = END_TURN，动作 24 = MOVE_TO（勿颠倒）
- 旧知识库曾写成"10=保留、24=结束回合"，与源码相反。
- 正确：`END_TURN = 10`，`MOVE_TO = 24`【来源：strategic_env.py L196, L211】。
- 见知识库 §二.3。

### 3.3 观测 3464 是状态向量，地形是独立输入
- obs **不含** 4×21×21 地形；地形以独立 `(4,21,21)` 栅格传入 CNN 第二输入 `model(obs, terrain)`。
- **来源**：strategic_env.py L235-236；train_wsl2_ppo_v2.py L152 `forward(x, terrain)`。

### 3.4 服务器 :8080 只能评旧 SB3 模型
- 80 个模型全是旧 256 维 SB3；新 3464 维 ONNX 能 load 但 predict 维度不兼容。
- **来源**：curl `:8080/health` 实测（current_model=`ppo_Key to Victory_h3m_500000steps`）。

### 3.5 VCMI 内置 AI 是进程内 cb 接口，非网络 client（T13 关键）
- VCMI 内置 AI（VCAI / Nullkiller / StupidAI）通过 `cb`（CPlayerSpecificCallback / Gateway）**进程内**直接跟 server 交互，是 server 侧逻辑的一部分；GitHub 生态里**没有现成的"纯 TCP 网络 AI client"第三方项目**可抄。
- **含义**：T13「外挂 AI 走 VCMI 网络协议接入」是**独特方向**，最接近的可参考实现是 VCMI 自己的 `client/` 目录（vcmiclient 如何实现 client 协议）——复用其序列化/收包逻辑，把"渲染+输入"层换成"AI 决策"。
- **来源**：vcmi.eu/developers/AI；DeepWiki vcmi/vcmi 2.1/8。**见知识库 §7.1**。

### 3.6 homm3tools 不碰 VMAP，H3M↔VMAP 翻译机只能是 VCMI
- `homm3tools` 的 `h3mconvert` 只做 H3M **版本间**（RoE↔AB↔SoD↔WoG）转换，`h3mlib` 解析 H3M 二进制；**整套不读不写 VCMI 的 JSON 格式**，README 零处提及 VCMI/vmap。
- H3M↔VMAP 唯一转换器是 VCMI（`CMapService` 按签名识别 + `CMapLoaderH3M`/`CMapLoaderJson`），你已用其把 H3M 转 VMAP 入训练池。
- **来源**：homm3tools README + HeroesCommunity 讨论；DeepWiki vcmi/vcmi Map System。**见知识库 §7.3**。
