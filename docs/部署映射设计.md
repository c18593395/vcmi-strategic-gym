# 部署映射设计 — VCMI 训练 → 原版 SoD 3.2 落地

> 日期: 2026-08-14
> 定位: 设计文档 (与 `动作空间设计文档.md` 配套)。目标是把训练好的战略模型部署到**原始英雄无敌3死亡阴影 (SoD 3.2)** 中真实运行 — 内存对齐 + 操作实现。
> 依据: 实测 H3API (RoseKavalier, 2025-03 维护中) 源码结构; VCMI 训练栈 (smanolloff fork)
> 原则: 训练 obs/动作是**游戏语义级**设计 (非 VCMI 内部结构), 与原版内存天然可映射。本文档钉死映射表, 防 Phase E 返工。

---

## 1. 三条部署路线 (决策背景)

| 路线 | 引擎 | 内存对齐 | 操作实现 | 工作量 | 适用阶段 |
|------|------|---------|---------|--------|---------|
| A. VCMI Windows | VCMI 引擎 (加载 SoD 数据) | 无 (引擎内直读) | CCallback 直接调 | 最小 | 先验证模型能赢 (Phase F 前) |
| B. C/S 多人联网 | VCMI 网络协议 | 无 | VCMI 网络包 | 中 | 人vs人vs模型 |
| C. **原版 SoD + H3API DLL** | 原版 Heroes3.exe (SoD 3.2) | H3API 结构体映射 | DLL hook 内部函数 | 大 | **最终真实落地** |

**本文档主写路线 C** (用户目标: 原始 SoD 中使用)。A/B 是中间态, obs/动作复用同一套游戏语义。

| heroes | movement/max_movement | `H3Hero.movement/maxMovement` | 🟢 直读 |

## 4. 动作码 ↔ 原版操作映射表 (64 码冻结版)

> 目标: 训练动作码每个在原版里找到执行方式。三类: ①内部函数 hook ②内存写+游戏自检 ③模拟输入 (最次选)。

| 动作码 | 名称 | 原版执行方式 | 方式 | 难度 |
|--------|------|-------------|------|------|
| 0-7 | MOVE 8 方向 | hook 移动函数 (H3Hero 目标坐标 + 原版移动循环) | ① | 🟡 |
| 8 | INTERACT | 模拟点击对象 / hook 访问函数 | ①③ | 🟡 |
| 9 | NEXT_HERO | `H3Player.currentHero` 内存写 | ② | 🟢 |
| 10 | END_TURN | hook 回合结束函数 (按回车同款) | ① | 🟢 |
| 11-13 | SPLIT×3 | hook 兵力分割函数 (H3Army) | ① | 🔴 |
| 14 | MERGE_FROM | hook 兵力合并函数 | ① | 🔴 |
| 15 | SWAP_ARMY | hook 交换函数 (英雄间/英雄-城镇) | ① | 🔴 |
| 16-18 | RECRUIT×3 | hook 招募函数 (`H3Town.recruits` 消耗) | ① | 🔴 |
| 19-21 | BUILD×3 | hook 建造函数 (建筑 bitfield + 资源扣减) | ① | 🔴 |
| 22 | GARRISON | hook 驻守/换将函数 | ① | 🟡 |

## 5. 操作注入架构 (路线 C 实现方案)

```
┌────────────────────── Heroes3.exe (SoD 3.2, x86) ──────────────────────┐
│                                                                        │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  AI DLL (我们的注入模块)                                          │   │
│  │  ┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐  │   │
│  │  │ 状态读取层        │  │ 动作执行层        │  │ 推理层           │  │   │
│  │  │ H3API 结构映射    │  │ hook 内部函数     │  │ ONNX Runtime    │  │   │
│  │  │ → obs 3456 维    │  │ → 64 动作码      │  │ 或 ctypes→训练端  │  │   │
│  │  └─────────────────┘  └─────────────────┘  └─────────────────┘  │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                        │
│  注入方式: 启动器注入 (LdrLoadDll) 或 修改版快捷方式 (H3Plugins 同款)     │
└────────────────────────────────────────────────────────────────────────┘
```

### 5.1 三层职责

| 层 | 职责 | 实现 |
|----|------|------|
| 状态读取层 | H3API 结构体 → 3456 维 obs (与训练端同一 schema) | H3API + 映射表 §3 |
| 动作执行层 | 64 动作码 → hook 原版函数调用 | 函数地址表 + hook |
| 推理层 | obs → 动作 (模型推理) | ONNX Runtime (模型已导出) 或 与训练端通信 |

### 5.2 推理部署两种形态

- **形态 1 (自包含)**: ONNX 导出模型 → DLL 内 ONNX Runtime 推理 → 完全独立运行, 无需训练端
- **形态 2 (联调)**: DLL 只做读写, 推理在训练端 (或服务器 172.16.2.40) — 训练/调参期间用, 部署切形态 1

## 7. 风险与对策

| 风险 | 概率 | 影响 | 对策 |
|------|------|------|------|
| 原版函数地址随版本漂移 (中文版/英文版/HotA) | 高 | 部署失效 | 锁定 SoD 3.2 英文原版; H3API 地址表为基线 |
| 分兵/招募函数逆向难度大 | 中 | E2 延期 | H3API 部分已提供; H3Plugins 有范例 |
| 内存写触发游戏自检 (防作弊) | 低 | 崩溃 | 优先 hook 函数 (游戏自检通常查 UI 层, 函数层安全) |
| 推理延迟影响回合操作 | 低 | 体验 | 回合制无实时压力; 决策 <1s 即可 |
| 多语言版本内存布局不同 | 中 | 部署范围 | 先锁英文版, 中文版另做偏移表 |
| 战斗裁决差异 (VCMI autofight vs 原版) | 中 | 胜率失真 | E 阶段用原版战斗评估, 训练时已知此偏差 |

## 8. 与训练设计的一致性保证

1. **obs/动作保持游戏语义级** (不绑定 VCMI 内部类名) — 已满足, 部署映射无需改设计
2. **观测 schema 同一份**: 训练端 (VCMI fill_strategic_state) 与部署端 (H3API) 输出**同一 3456 维布局** — 双端对照测试 (动作空间设计文档冒烟 #16 扩展)
3. **动作码表同一份**: 训练端 (AAI.cpp) 与部署端 (hook 层) 用同一 64 码表 — 部署端是执行器替换, 模型零改动
4. **奖励/评估同一标准**: 部署端可用 H3AI SimulatedCombat 做战前评估, 与训练端 battle_pred 对齐

**核心保证**: 模型训练完成后, 部署 = 换执行器 (VCMI CCallback → H3API hook), obs/动作/模型推理全部复用, 不重新训练、不改网络结构。
