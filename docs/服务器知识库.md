## 一、项目概述

**目标：** AI 完整操控 HoMM3 真实游戏，与你对战（1v7），并战胜你。

**策略：** VCMI 沙盒训练战略模型 → 真实游戏内存操控 → 自对弈持续进化。

**当前阶段（新项目架构）：** PPO 自对弈长程训练（WSL2, RTX3060, x86），观测 **3464 维**（含 4×21×21 地形 CNN 特征）、动作 **25**、自定义 `Net`；`train_wsl2_ppo_v2.py` 24/7 运行，checkpoint 每 50 step 落 `checkpoints/wsl2_ckpt_<step>.pt`。服务器 `172.16.2.40` 仅作模型仓库 + WIN RATE 结果中枢（详见 §十五，旧架构跑不了新模型）。

## 三、关键技术决策

### 3.1 两段式设计

```
训练端 (WSL2):  /home/administrator/vcmi-workspace/, MMAI ON, RTX 3060
推理端 (ARM64): root@172.16.2.40, 不需要 callback, ctypes 直读状态 + ONNX 推理
部署端 (真实游戏): 本机 HD Mod, 内存读取 + PostMessage, 模型推理
```

### 3.2 为什么放弃 ARM64 训练

**根因：** headless=true 下 VCMI 的 `networkHandler->createTimer()` 不触发，游戏不进首回合。
**尝试过：** ctypes→connector 迁移、DummyVecEnv 短路、MLClient 注入 mainLoop、Xvfb —— 全部失败。
**结论：** 根源在 VCMI 服务线程网络层事件循环，涉及 `lib/client/GameEngine.cpp`、`lib/server/CVCMIServer.cpp`、`lib/network/` 源码改造，不确定性大。
**决定：** ARM64 留作推理端，训练全部移到 WSL2。

### 3.3 为什么选 Nullkiller2 而非 MMAI

- MMAI (Mini AI) 模块在 WSL2 上初始化阶段 core dump
- MMAI 含 broken `g_cached_game_state` 代码，清理后依然不稳定
- Nullkiller2 是 VCMI 内置冒险 AI，稳定且已有 AIGateway.cpp 回调钩子
- 切换方式：`ENABLE_MMAI=OFF`, `ENABLE_NULLKILLER2_AI=ON`

### 3.4 战略训练只用 H3M，不用 vmap

**历史教训：** 早期用 vmap（战斗模型训练图）跑战略训练，大部分 vmap 不是 2-player 布局，导致 adventure 回调不来或崩溃。
**原则：** 战略训练只用 H3M 经典图。
**现状：** scan_maps.py 从 158 张中筛出 110 张可用 2-player H3M。

### 3.5 观测与动作（新项目架构）

- **观测 3464 维（冻结铁律）**，由 `vcmi_gym/envs/v13/strategic_env.py` 的 `StrategicEnv` 生成：含 4 通道 21×21 地形特征图（1764 维）+ 状态向量（英雄/城镇/资源/敌方可见信息/日期/8 方向 passability 等）。`_test_suite M6 修复`曾误写 3456 维，已校正为 3464。
- **动作空间 25**（见 `strategic_env.py: N_ACTIONS=25`）：
  - 0-7：8 方向移动（受 `obs[3211:3219]` passability 约束）
  - 8：交互（INTERACT，冷却约束）
  - 9：下一英雄（永久屏蔽）
  - 10：保留动作（当前 env 未强制屏蔽；具体语义以 `py/ep_runner_one.py` 屏蔽段为准）
  - 11-15：永久屏蔽（底层无执行分支）
  - 16-18：招募 RECRUIT_1/2/3（仅 T04 地图开启，受 `obs[640:672]` recruit_mask 约束）
  - 19-21：建造 BUILD_1/2/3（仅 T04 地图开启，受 `obs[672:704]` build_mask 约束）
  - 22：驻军 GARRISON（屏蔽）
  - 23：招募英雄 RECRUIT_HERO（屏蔽）
  - 24：结束回合 END_TURN
  - **动作屏蔽以 `py/ep_runner_one.py` 永久屏蔽段为训练真源**，评测器 `py/winrate_eval.py` 的 `masked_argmax` 必须镜像该逻辑。
- AI 对手（蓝方）使用 Nullkiller2 或 MMAI（由 `--blue` 指定），不耗 RL 推理；红方由 `Net` 控制。
- ⚠️ **旧架构（历史）**：SB3 老模型用 256 维观测 / 11 动作（0-7 移动、8 交互、9 下一英雄、10 结束回合），对应服务器旧 `v13` 引擎，新项目已弃用。

### 3.6 step() 通信机制（C7 最终架构 + B 修复 + #45 修复）

```
Python step(action):
  ① _send_action(action)        // 发 action 给 VCMI（写 atomic s_turn_action）
  ② _adventure_wait()           // 等 VCMI 处理完在下一轮 process_turn 阻塞
  ③ _read_state()               // 读状态（从 cb 方法填充，非 CGameState）

C++ yourTurn() → 单次 action:
  ① adventure_process_turn()    // 阻塞等 Python 发 action（spin-loop）
  ② adventure_get_action()      // 从 atomic 读 action
  ③ switch(action): moveHero    // 直接 cb->moveHero（selectionMade 之前）
  ④ cb->selectionMade(queryID)  // 回答 query
  ⑤ fill_state_from_cb(cb)      // 用 cb 方法填充 state（绕过 CGameState!）
  ⑥ compute_passability_cb(cb)  // 用 cb->canMoveBetween 算 passability
  ⑦ cb->endTurn()
```

**修复 #45 的关键（2026-07-28）：**
- `strategic_state_update(&igic->gameState())` → **空**，因为客户端 CGameState 在 yourTurn 时未同步
- 替换为 `fill_state_from_cb(cb)`，使用 `cb->getHeroesInfo()`、`cb->getPlayerState()`、`cb->getResource()` 等方法直接填充
- `cb->getHeroesInfo()` 一直有数据（moveHero 用它成功了 5000+ ep），但之前 strategic_state_update 走错了数据源

**#45 实际阻塞点（2026-07-28 发现）：**
- ep_runner 子进程 `stderr=subprocess.DEVNULL` → MMAI 的所有 `fprintf` 诊断全丢弃
- VCMI 内部重定向 stdout/stderr（CBasicLogConfigurator），MMAIA DIAG 输出不可见
- 改用写文件 `/tmp/mmai_diag.txt`（fopen+fprintf+fclose 绕过 VCMI 日志层）可见诊断
- **更深层问题**：connector_v13 与 libmlclient 的 `init_vcmi` ABI 不一致（3-arg vs 1-arg）
- connector 代码用旧 3-arg API，libmlclient 已改为 1-arg void* → 运行时 core dump
- connector 编译时 CMakeLists.txt 第 11 行 `set(VCMI_DIR /home/administrator/vcmi-native)` 硬编码覆盖 `-DVCMI_DIR`
- connector 必须与 libmlclient/MMAI 编译自同一 schema 版本（BATTLE_ROUND vs BATTLE_SIDE 冲突）

**关键不变：** SEND→WAIT→READ 顺序，无 race condition。state_update 在 process_turn 阻塞后执行，Python 在 _adventure_wait 返回后才读状态。

### 3.7 C7 动作映射架构

> 本节描述 v13 旧架构底层通信机制（`g_rl_action` / `adventure_process_turn` / `AAI.cpp`），**新架构仍沿用这套 C++ 通信骨架**；但观测维度已从 256 升级为 **3464**（`StrategicEnv` 组装，见 §三.5），`strategic_state_update` 接口在 #45 修复后已废弃（改用 `fill_state_from_cb`，见 §三.6）。

```
Python PPO policy (model)
    ↓ action
strategic_env.py step()
    ↓ ctypes 写 g_rl_action + adventure_send_action
C++ adventure_process_turn spin 退出
    ↓ read g_rl_action
AAI.cpp yourTurn → cb->moveHero() 直接执行
    ↓
cb->endTurn() → VCMI 推进到下一玩家
```

| 组件 | 位置 | 作用 |
|------|------|------|
| g_rl_action | strategic_state.h/cpp | 全局变量，Python ctypes 写入，C++ 读取 |
| adventure_process_turn | strategic_state.cpp | spin-loop 等 Python action |
| adventure_get_action | strategic_state.cpp | 读 g_rl_action |
| strategic_state_update | strategic_state.cpp | **已废弃（#45 后）**：原从 CGameState 填充观测；新架构改用 `fill_state_from_cb`，且观测维度为 3464（非 256） |
| AAI::yourTurn | AI/MMAI/AAI/AAI.cpp | 红方控制枢纽：fill_state_from_cb → process_turn → moveHero → endTurn（旧描述写作 state_update，已更正） |
| ServerPlugin start/endBattleHook | server/ML/ServerPlugin.cpp | 战斗钩子，hero2=null 时跳过（防崩） |

**非红方（蓝方）**：AAI.cpp 的 pc!=0 guard 直接 endTurn，不进 while 循环。蓝方由 VCMI 内置 AI（MMAI）控制，但拦截后直接结束，不会和 Python 交互。

### 3.8 战斗处理

英雄踩怪物：
1. startBattleHook(hero1, hero2=null) → return（跳过 ML 随机初始化）
2. VCMI autofight 自动裁决
3. endBattleHook(heroDefender=null) → return（跳过 stats 记录）
4. 战斗完成，继续 turn 循环

### 4.9 服务器旧架构跑不了新模型 → WIN RATE 必须回 WSL2（架构约束）

| 项目 | 内容 |
|---|---|
| 根因 | 服务器 `/DATA/hero3/vcmi-build/bin/*.so` 是 ARM64 编译的旧 v13 架构（obs 256 维 / 11 动作）；新模型 obs 3464 维 + 4×21×21 地形 CNN + 25 动作，维度与 ABI 都不兼容 |
| 表现 | 推到服务器无法用 `batch_eval` 评新模型；`:8080` 能 load 新 ONNX 但 `predict` 只支持单输入 256 维旧模型 |
| 结论 | WIN RATE 评测只能在 WSL2（唯一 x86 带新引擎的机器）跑，结果回传 `:8088` 集中存放；不要迷信"推到服务器评测" |

### 4.10 本机 WorkBuddy sandbox 禁用 wsl.exe → WSL 侧脚本只能写不能跑（环境坑）

| 项目 | 内容 |
|---|---|
| 根因 | 本机 sandbox 把 `wsl.exe` 列入 Program Blacklist，执行报 `PROGRAM BLOCKED BY SECURITY POLICY` |
| 影响 | 任何需在 WSL2 内运行的脚本/命令（含 `wsl -d Ubuntu`、训练、评测）都无法在此环境端到端验证 |
| 处置 | 只写文件（WSL 经 `/mnt/d/` 可见）交用户/WSL 内实跑；语法校验用 Windows 侧 `python -m py_compile` / `bash -n` 兜底；跨机链路文档标注"未在此环境跑通" |

### 4.11 ckpt_push_hook.py 的 global 声明顺序 bug（已修复）

| 项目 | 内容 |
|---|---|
| 根因 | `main()` 内先 `default=SERVER` 引用全局，下方才写 `global SERVER,...`，Python 报 `SyntaxError: name 'SERVER' is used prior to global declaration` |
| 修复 | `global` 上移至 `main()` 顶部、置于任何引用之前；移除非重赋值项；顺带显式 `import urllib.error`（原仅靠 `urllib.request` 传递导入） |

```bash
# 三件套同源编译（必须！）
cd ~/vcmi-native
cmake .. -DENABLE_ML=ON -DENABLE_MMAI=ON -DENABLE_NULLKILLER2_AI=ON

cmake --build . --target mlclient -j4
```

## 十一、StrategicState 结构体布局（C++ ↔ Python ABI，旧 v13 架构 ⚠️）

> ⚠️ 本节结构体为 **SB3 老架构** 的 256 维观测编码（C++ `libmlclient.so` 侧），对应 connector v13。**新架构观测已升级为 3464 维**，由 Python 侧 `StrategicEnv` 组装，不再直接依赖此 C++ 结构体布局（见 §三.5 / §五）。本节保留作 C++↔Python ABI 历史溯源，字段偏移仅供旧引擎排障参考。


- `game_over` @ 2336

## 十二、数据流（修复后，旧 v13 架构 ⚠️）

> ⚠️ 本节为 SB3 老架构修复后的数据流。**#45 修复（2026-07-28，见 §三.6）已将 `strategic_state_update(CGameState*)` 改为 `fill_state_from_cb(cb)`**（绕过 CGameState，直接用 `cb->getHeroesInfo()` 等方法填充），且新架构观测维度为 **3464**（非 256）。新项目数据流：VCMI → `AAI.cpp yourTurn` → `fill_state_from_cb` → `StrategicEnv` 组装 3464 维 obs → `Net` 输出 25 维 action → `adventure_send_action` 写原子变量 → 等待下一轮。

## 十四、#45 Connector ABI + Schema 统一修复（2026-07-28/29 开机修复，旧 v13 架构历史 ⚠️）

### 核心问题链
1. CMakeCache 残留旧 `VCMI_DIR=/mnt/d/Bigdata/hero3_fresh/vcmi`（项目旧版源码），但 CMakeLists.txt 硬编码 `set(VCMI_DIR "/home/administrator/vcmi-native")` → **`set()` 不覆盖已缓存变量**，必须 `rm CMakeCache.txt` + 显式 `-DVCMI_DIR=...`
2. 源码三副本不一致：
   - `vcmi-native/`（工作源码 — 被回退过）
   - `vcmi-native-build/`（cmake 源目录 — 与二进制匹配）

4. Binary 是 BATTLE_ROUND schema，但 connector 被编译时用了 BATTLE_SIDE header → schema 字段偏移不符 → segfault
